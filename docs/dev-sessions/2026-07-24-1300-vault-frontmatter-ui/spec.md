# Spec: vault page frontmatter rendering and editing

## Problem

Vault pages now carry real frontmatter — `summary`, `keywords`, `tags`,
`importance`, generated by #197's self-improving vault arc. The web UI has no
idea. Nothing in `web/` imports `frontmatter.py`; `GET /api/vault/{page}`
returns the raw file and both display paths treat the YAML as markdown.

**View mode** (`wiki-page.js:310`) pipes the whole file through `marked`. The
opening `---` becomes an `<hr>`, and the YAML flattens into a bullet list where
adjacent keys collide into single items — `personal workflow summary: This page
summarizes… tags:` renders as one bullet.

**Edit mode is worse than cosmetic.** Milkdown loads with
`commonmark/gfm/history/listener/clipboard/wikiLink` and no frontmatter plugin
(`wiki-editor.js:113-118`). It parses the YAML into ordinary markdown nodes,
and `getMarkdown()` serializes those nodes back on save. So editing a page with
frontmatter through the web UI **writes the mangled version to disk**, and
`vault_write` then reindexes embeddings on the corrupted text. The `md !== prev`
listener at `wiki-editor.js:109` may fire on initial load, meaning merely
opening a page could corrupt it — unverified, and the first thing the
implementation must pin down with a test.

This is a data-loss bug wearing a rendering bug's clothes.

## Design decisions (approved at brainstorm)

- **Frontmatter is chrome, not content.** The server splits it off; the body
  reaches `marked`/Milkdown alone. Milkdown never sees YAML, so it cannot
  mangle it — the fix is structural, not careful.
- **Mirror the schedules pattern.** `/api/schedules/*` already does exactly
  this split: `_schedule_payload` (`http_server.py:1909`) returns a
  frontmatter-stripped `body` plus typed metadata fields, PUT aliases
  `content` → `body` (`:1942`), and metadata edits go through per-field patches
  (`schedule-page.js` `#patchField`) rather than through the editor. Vault
  pages follow it rather than inventing a second convention.
- **Server-side split, not client-side.** Rejected: client-side YAML parsing
  needs a `js-yaml` vendor dependency and would diverge from `frontmatter.py`'s
  round-trip fidelity, leaving every client one bug from corrupting files
  again. Also rejected: a Milkdown atom node holding the YAML verbatim — the
  most code, the most Milkdown-specific knowledge, and a serializer bug still
  writes bad files. The server-side split also means `wiki-editor.js` needs
  **zero** changes.
- **Typed controls for known fields, raw YAML for everything else.**
  `docs/vault.md:72` states the frontmatter schema is deliberately informal and
  unknown keys are preserved. Typed controls cover `summary`, `importance`,
  `tags`, `keywords`; a raw-YAML editor covers everything else so nothing is
  silently dropped.
- **The raw block holds the entire frontmatter, with replace semantics.**
  Rejected: scoping it to unknown keys only, which needs a key-partitioning
  rule, wholesale replacement of the non-known key set, and a 400 for
  collisions when someone types `summary:` into it — three rules and an error
  case for the same capability. Whole-frontmatter replace is one rule. Cost:
  deleting a known key in the raw block really deletes it, which is honest
  behavior for a raw editor.
- **Body saves re-attach the frontmatter block lexically, verbatim.** Not via
  `serialize_frontmatter`. See "Why body saves must not reserialize" below —
  this is the decision the rest of the correctness rests on.
- **Compact read-only strip in view mode, expandable.** Summary, importance,
  tag chips visible at a glance; the body stays the focus.
- **Tag chips are display-only this session.** See "Relationship to #318".

## Relationship to #318 (first-class vault tags)

#318 is open and in-flight in the `318-vault-tags` worktree (session
`2026-07-24-1141-vault-tags`, three of six phases committed, no PR yet). Its
plan reserves **Phase 5** for a `/api/vault/tags` endpoint and **Phase 6** for
a web UI Tags tab. `tags.py` already ships `normalize_tag` and
`pages_with_tags(config, tags, any_tag=False)`.

Clickable tag chips were considered for this session and **cut**. A
`vault_list?tag=` query here would be a weaker parallel implementation:
frontmatter-only (no inline Obsidian `#tags`), no AND/OR, and its own
normalization semantics competing with #318's settled ones (lowercase
canonical, first-seen display casing preserved, no `-`/`_` merging). Chips
render as static, styled elements with the markup and CSS a click handler will
need; #318 Phase 6 wires them to `pages_with_tags` when it builds the Tags tab.

**Coordination note:** #318 also edits `frontmatter.py` and introduces a
deliberate `frontmatter.py` ↔ `tags.py` import cycle (documented at
`build_composite_text`, with a function-level import breaking it). This
session's additions to `frontmatter.py` land in different regions of the file,
so the branches should merge, but whichever lands second should expect to
resolve there. `split_frontmatter` must stay purely lexical with no `tags`
import so it does not deepen that cycle.

## Architecture

### `frontmatter.py`

**`merge_frontmatter` moves here** from `skills/vault/tools.py:1167`. Its
function-level `from decafclaw.frontmatter import get_frontmatter_field`
disappears — same module now — which is the correct outcome, since CLAUDE.md
restricts function-level imports to breaking cycles and this one existed only
because the helper sat in the wrong file. `backfill_frontmatter.py:30`, a core
CLI, already reaches into the skill package for it; `http_server.py` needing it
makes three call sites. Behavior is unchanged: the scheduled dream/garden paths
and `vault_update_frontmatter` keep their exact current semantics.

**New `split_frontmatter(text) -> (raw_block: str | None, body: str)`** — pure
regex, no YAML parse, sharing `_FRONTMATTER_RE` with `parse_frontmatter`.
Returns the frontmatter block's original bytes (delimiters included) or `None`
when absent.

### `GET /api/vault/{page}`

Gains `frontmatter` (parsed dict), `frontmatter_raw` (the block's original text,
delimiters excluded, `""` when absent), and `body` (frontmatter-stripped).
**Drops `content`.** The only consumer is `wiki-page.js`, and a stale full-file
field is exactly what rots into a second corruption path.

`frontmatter_raw` is returned **always**, not only on error — the raw-YAML
editor has replace semantics, so its textarea must be seeded with the real
bytes. Re-serializing the parsed dict client-side would silently reorder keys
and drop comments the moment someone opened the panel.

On malformed YAML, returns `frontmatter: {}`, `frontmatter_raw` unchanged, and
a `frontmatter_error` string carrying the parse message.

### `PUT /api/vault/{page}`

Four shapes; `rename_to` stays mutually exclusive as it is today.

| Field | Meaning |
| --- | --- |
| `content` | Aliased to `body`, as schedules does at `:1942`. **Body-only**: the server re-reads the file, splices the original frontmatter block back verbatim, and writes. |
| `body` | Same as `content`. |
| `frontmatter` | Dict. Partial **patch**, merged via `merge_frontmatter(existing, fields, overwrite=True)`. `overwrite=True` because a human editing a field is explicit intent, unlike dream's fill-absent-only pass. Backs the typed controls. |
| `frontmatter_raw` | String. **Replace**: parsed with `yaml.safe_load` and written as the complete frontmatter, no merge. Backs the raw-YAML editor. |

Note the deliberate asymmetry on `content`: the GET response drops it while PUT
still accepts it. That is what lets `wiki-editor.js` stay untouched — it keeps
sending `{content, modified}` and the server reinterprets it as a body-only
write, exactly as the schedules endpoint already does.

`frontmatter` and `frontmatter_raw` are **mutually exclusive** — patch and
replace cannot be reconciled in one write, and accepting both would make
precedence a coin flip. Sending both is a 400.

Either may arrive together with a body — applied frontmatter-then-body, one
write, one mtime bump, one reindex.

The response returns the resulting frontmatter and the new `modified`.

**Key deletion.** The two paths delete differently, and both need to work:

- `frontmatter_raw` deletes by omission — replace semantics, so a key absent
  from the submitted YAML is gone. This is the primary deletion mechanism.
- `frontmatter` cannot delete by omission, since a patch says nothing about
  keys it omits. It deletes via an explicit `null` value — which
  `merge_frontmatter` does not support: `get_frontmatter_field({f: None}, f)`
  returns `None`, so the merge writes a literal `field: null` rather than
  removing the key. The API layer pops null-valued keys off the merged dict
  before serializing, leaving `merge_frontmatter` exactly as the scheduled
  dream/garden paths expect it. This is what fires when the UI clears the last
  tag.

### Why body saves must not reserialize

`serialize_frontmatter(parse_frontmatter(text)[0], new_body)` is the obvious
implementation and it is wrong twice over:

1. `parse_frontmatter` returns `({}, body)` on `yaml.YAMLError`
   (`frontmatter.py:41`) — it strips the block and reports empty metadata. On a
   page with hand-broken YAML, a body-only save would call
   `serialize_frontmatter({}, body)` and **silently delete the frontmatter**.
   That ships a second corruption path while fixing the first.
2. `yaml.dump` defaults to `sort_keys=True` and drops comments, so every body
   edit would churn the YAML formatting even when metadata is untouched.

Splicing the raw block back verbatim fixes both: key order, comments, and
malformed YAML all survive, and `yaml.dump` runs only when the user is actually
editing metadata, where reformatting is expected.

### `wiki-metadata.js` (new component)

Joins the `wiki-page` / `wiki-editor` family. Presentational: takes
`.frontmatter`, `.frontmatterRaw`, `.frontmatterError`, and `readonly`; emits
`metadata-change` with a partial-fields patch and `metadata-raw-save` with the
raw YAML text.

**`wiki-page` owns the PUT, not the component.** It has to push the response's
new `modified` into `<wiki-editor>` so the body autosave does not 409 on the
next keystroke — the same coordination `schedule-page.js:129` documents in
reverse.

Controls:

- `summary` — autosizing textarea
- `importance` — range slider, 0–1 step 0.05, with numeric readout
- `tags`, `keywords` — chip inputs; remove via per-chip button, add via text
  input on Enter or comma
- everything else — a raw-YAML textarea holding the **entire** frontmatter,
  saved by an explicit button, not debounced, since half-typed YAML is invalid
  YAML

Typed edits debounce ~600ms then PUT `frontmatter`. The panel re-renders from
the response's frontmatter rather than optimistically, so `merge_frontmatter`'s
coercion (importance clamped to [0,1], tags normalized to `list[str]`) is
visible instead of silently disagreeing with what was typed.

**A raw save must flush any pending typed debounce first.** The two PUT shapes
are mutually exclusive, and raw is replace — a typed patch landing *after* a
raw replace would resurrect a key the raw save just deleted. `wiki-page` awaits
the pending patch (or cancels it, if the raw text already reflects it) before
issuing the raw PUT, the same ordering discipline `wiki-editor.flushSave()`
applies before page switches.

Read-only mode is the same component with `readonly`: clamped summary,
importance value, tag chips with `+N` overflow. Expand state persists in
`localStorage` alongside the existing `wiki-edit-mode` key.

On `frontmatter_error`, the raw editor opens pre-populated with the parse error
inline and the typed controls are disabled. Body editing still works safely
because it never touches the block.

### `wiki-page.js`

Consumes `body` instead of `content`, renders `<wiki-metadata>` above the
body in both modes, owns metadata PUTs, and pushes `modified` into
`<wiki-editor>` after each.

The `if (!this._content) return nothing` guard at `:236` becomes an explicit
`_loaded` flag — otherwise a page with frontmatter but an empty body renders as
blank nothing.

### Sidebar summaries

`vault_list` parses frontmatter per page in the requested folder and adds
`summary` to each row; `vault_recent` gets the same treatment so both flat
lists show subtitles consistently. Folder-scoped, and the whole vault is 276
pages / 1.3 MB, so cost is not a concern.

`vault-sidebar.js` renders the summary as a row subtitle. Rows stay plain
`<div @click>` per the convention these sidebars share; the cross-cutting a11y
fix is #555 and is not in scope here.

## Error handling

| Case | Behavior |
| --- | --- |
| Malformed YAML on disk | `frontmatter_error` + raw block in GET; raw editor opens with the error inline, typed controls disabled; body editing unaffected |
| Raw YAML parses to a non-mapping | 400. `parse_frontmatter` logs and ignores this at `:38`; the API rejects explicitly rather than inheriting the silent-ignore |
| Raw YAML malformed | 400 carrying the `yaml.YAMLError` message; the file is left untouched |
| Raw YAML empty | Frontmatter block removed. Legitimate, allowed |
| `frontmatter` and `frontmatter_raw` both sent | 400 — patch and replace cannot be reconciled in one write |
| Stale `modified` on a metadata PUT | 409, with the same reload/overwrite affordance as `wiki-editor.js:334`. A merge against a stale read would otherwise resurrect a just-deleted key |
| Body's own first line is `---` | Safe: `_FRONTMATTER_RE` is non-greedy and anchored at `\A`, so it matches the real block |
| New page, bare `content`, no existing file | No frontmatter invented |

## Testing

No JS unit-test harness exists — `make check-js` is `tsc --checkJs` only — so
the JS side is typecheck plus a Playwright smoke, and the assertions live in
Python.

**Write first, per the bug-fix convention:** in `tests/test_vault_api.py`,
write a page with frontmatter, PUT a body-only change, assert the frontmatter
block is **byte-identical** on disk. This is the guarantee the design exists to
provide and it fails today.

Two siblings guard the reserialization findings:

- malformed YAML survives a body save verbatim
- a block with non-alphabetical keys and a `# comment` survives a body save —
  this is what catches a regression back to `yaml.dump` on the body path

API surface:

- GET returns `frontmatter`, `frontmatter_raw`, and `body`, with the block
  excluded from `body` and `frontmatter_raw` present on well-formed pages too,
  not only on error
- GET on malformed YAML returns `frontmatter_error` plus the raw block
- PUT `frontmatter` merges and returns the coerced result — importance `1.7` →
  `1.0` proves `merge_frontmatter` is genuinely in the path
- PUT `frontmatter` with a null value removes the key rather than writing
  `field: null`
- PUT `frontmatter_raw` **replaces** — a key present on disk but absent from
  the submitted YAML is gone afterward, which is the test that distinguishes
  replace from merge and would fail if the raw path were wired to
  `merge_frontmatter`
- non-mapping raw YAML → 400
- malformed raw YAML → 400, file unchanged on disk
- empty raw YAML → block removed
- both `frontmatter` and `frontmatter_raw` → 400
- `frontmatter` + body together apply in one write
- stale `modified` → 409
- `test_vault_write_new_page` stays untouched, proving a bare `content` POST to
  a nonexistent page still invents no frontmatter

`split_frontmatter` unit tests in `tests/test_frontmatter.py`: absent block,
empty block, malformed block, and a body whose own first line is `---`.

Sidebar: `vault_list` includes `summary` and omits it cleanly for pages without
frontmatter.

`merge_frontmatter`'s move is covered by re-pointing its existing tests plus
`tests/test_backfill_frontmatter.py`, which imports it through the old path.

**No evals.** CLAUDE.md says skip them for non-LLM-visible work: no tool
descriptions change, no system-prompt change, no new tools.
`merge_frontmatter` relocating does not alter `vault_update_frontmatter`'s
behavior or description.

**Manual verification:** Playwright against the real vault, using the `0din`
page as the fixture — view mode, edit mode, and a body edit followed by
`git diff` on the file to confirm the frontmatter did not move. Requires
`make dev` stopped first; Playwright and dev share a Chrome cache dir and
collide.
